## Epic Review

Epic 1 is complete based on story-level status in `/home/pinto/repo/BMADGraphWebApp/_bmad-output/implementation-artifacts/sprint-status.yaml`: Stories `1-1` through `1-7` are all `done`. The tracker's `epic-1` row lagged behind that reality before this retrospective and should be treated as a workflow-sync gap rather than incomplete delivery. This is the first epic retrospective, so there is no prior retro to compare against.

The strongest success pattern was the contract-first foundation. Stories 1.1 through 1.3 established canonical schemas, kernel boundaries, and local persistence before feature breadth expanded, and later stories repeatedly benefited from that decision. Stories 1.4 through 1.7 then hardened the shell and trust surfaces with the same bias: fail closed when compatibility, metadata, or route ownership is unclear; keep valid state available; localize invalid state into explicit issue records. That pattern is visible across shell readiness, reopen validation, and thin bootstrap delivery.

The clearest recurring friction was edge-case pressure arriving through review. Epic 1 repeatedly uncovered stale metadata, compatibility drift, persisted-state reconciliation gaps, non-canonical path handling, and reopen repair edge cases after the first implementation pass. Stories 1.5, 1.6, and especially 1.7 show the same cycle: narrow the contract, add a precise regression test, then harden the implementation around fail-closed behavior. The review loops were productive, but they also show that trust-sensitive paths need adversarial coverage earlier instead of only after broad implementation lands.

Concrete lessons and action items:

- Keep canonical contracts as the single source of truth for shell metadata, workspace snapshots, issue records, and compatibility rules. Epic 1 went better when delivery, tests, and runtime code all consumed the same contracts.
- Preserve the "valid state stays usable, invalid state becomes explicit" rule. That approach worked for reopen validation and should remain the default for future trust-sensitive workflows.
- Add targeted adversarial coverage earlier for path aliasing, stale metadata, retained handles, and partial-state recovery. Epic 1 paid this cost late several times.
- Treat scope correction as a strength, not a failure. Deferring transform and graph-composition reopen validation from Story 1.5 into Story 1.6 reduced ambiguity and produced a cleaner contract boundary.
- Add a workflow hygiene check that promotes epic-level sprint status when all child stories are `done`, so tracker state does not drift from story reality.

## Next Epic Preparation

Epic 2 is well-positioned to start because Epic 1 now provides the prerequisites it depends on: a stable local workspace model, explicit trust/readiness selectors, reopen localization, and an owned shell bootstrap path. Story 2.1 depends directly on Story 1.3, and the rest of Epic 2 builds on the same contract-first and trust-first seams established here.

The main preparation need is to avoid creating a parallel intake architecture. Import preview, uncertainty handling, semantic correction, and onboarding should reuse the existing kernel, issue-record, readiness, and repair patterns instead of inventing separate state and warning systems. Epic 1 showed that duplicated logic or loosely enforced contracts become expensive once compatibility and reopen behavior matter.

Concrete action items for Epic 2:

- Define the preview-workspace and commit boundary explicitly before Story 2.1 implementation expands, so preview state does not fork from the canonical workspace model.
- Start with dirty-data and uncertainty cases, not only happy-path imports. Epic 1 shows late edge-case discovery creates repeated review churn.
- Reuse shared issue and readiness surfaces for import uncertainty, malformed data, and recovery guidance so trust behavior stays consistent from intake through reopen.
- Lock keyboard-accessible and guidance flows early in Stories 2.3 and 2.4. Epic 2 acceptance criteria already require accessible recovery and onboarding, and Epic 1 showed late trust-surface retrofits are expensive.
- Keep dev, preview, and deployed delivery parity under test whenever intake depends on shell bootstrap metadata or protected-route behavior.
